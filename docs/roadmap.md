已发现但未修的缺陷记在 [known-issues.md](known-issues.md)，那里同时记了**怎么检测**每一类静默失败

## 建议优先做

### 1. changelog 系统重建

2026-08-08 讨论的结论，实现待定。**优先级高于搜索。**

#### 旧系统为什么死了

笑笑设计了一套 `.txt` DSL（`version` / `cat` / `subcat` / `[]` 可链接实体），当 leader 时强制
所有开发者写，再用工具读进百科。他下台后没人再写，成了 repo 里的死代码；百科也一并没人维护，
后来转到我们手上。

但数据显示的病因**比「权威消失」更早**：

```
xiaoxiao.txt   683 行  10 个 version   ← schema 作者本人
time.txt       718 行  11 个 version   ← 另一个真在用的人
xhh.txt        171 行   6 个 version
其余 12 个      4~69 行  1~3 个 version  ← 写了一两次就停了
```

**大部分人在他还在任时就已经不写了**，只有 2/14 持续使用。所以这不是「权威撤离后崩溃」，
是**从来没被采纳，只被短暂服从过**。

根因是成本收益错配：写的成本落在 N 个开发者身上，收益落在 1 个百科维护者身上。这种结构
只能靠权威维持。**新方案的唯一硬指标：在没有任何人配合时，它还能不能运转。**

#### 方案：两个源互相校验

**源 A — 百科产物 diff（覆盖进百科的内容）**

`E:\HDCivilopedia_history`（快捷方式 `E:\hdciv\history.lnk`）下有 20 个历史发布产物，
从 `HDCivilopedia_1.3.9_workshop` 到 `HDCivilopedia_20260807`。相邻两个版本的产物 diff
**按定义就是玩家可见的变更集**——纯重构（比如 `insert or replace` → `insert or ignore`）
产生零 diff，`+2 生产力` 正好产生一条。信噪比问题被结构性消除，不靠 agent 去猜哪些行重要。
而且产物里已经是本地化名称和解析后的数值，天然是玩家语言。

> **不要用 `backup/Cache_*` 重建。** 试过这条路，是错的：Cache 是**游戏自己的 database**，
> 而 `Init.loadDLCs()` 会在其上重新加载**磁盘上当前的** mod 和 DLC。老 Cache + 今天的 mod
> 文件跑出来是个嵌合体，既不是当时的百科也不是现在的。必须用归档的最终产物。

**源 B — QQ 群更新公告（覆盖不进百科的机制改动）**

开发者每次更新会在群里发 @所有人 的公告。这是**已经存在、不需要任何人额外付出**的意图来源，
而且本来就是写给玩家看的。

**两个源的差集本身就是产出**：

- 产物 diff 有、公告没提 → 未公示的改动（玩家最容易抱怨的那类）
- 公告说了、产物 diff 没有 → 要么是机制改动（正常收下），要么是**公告吹了但没真正生效**

#### 开发者需要做什么：零

不用 AI、不装工具、不学格式、不改习惯。**AI 只在维护者这边跑**，所以「国内不方便用 agent」
这个约束根本不落在他们身上。

真正需要人的只剩 Lua 机制改动（不进数据库，产物 diff 看不见），而 git 能定位到是谁碰的哪个文件。
所以问题从「所有开发者、每次提交」缩成「**每个版本，问 1~2 个碰过 Lua 的人，几句话**」。

对付惰性靠四条结构性设计：

1. **推变成拉。** 旧系统要他们主动写；新系统是把一句话递到面前问「这样理解对吗」。
   懒人不会 push，但会回。
2. **默认发布。** 不回复也照发。旧系统里沉默 = 零，新系统里沉默 = 有草稿、置信度低一点。
3. **草稿写得略微不准是最有效的催化剂。** 不肯写 changelog 的人，看到自己的东西被描述错了
   一定会来纠正——用在意胜过用纪律。
4. **在他们已有的渠道问**（QQ/微信），不是 GitHub、不是文件、不是任何要符合语法的东西。
   一旦要求他们产出格式，就退回旧系统了。

#### 前置：归档自动化 —— **已完成**

`tools/Archive.java`，`page` / `after_init` 跑完自动执行，也可以 `Main archive` 单独跑。
写到 `archive.folder`（config.properties，不配就跳过）下的 `snapshots/<yyyyMMdd>/`，
**同一天只保留当天最后一次**，和顶层那 20 个手工发布归档分开放。一次 15~17s、65 MB：

- `json/` 原样复制（21 MB）——**diff 的正源**。HTML 不好 diff（一个数值变化牵动一堆
  `<span>`/`<a>`/表格标记），历史那 20 个只有 HTML，只能走「剥标签取正文再比」的路径
- `output/` 和 `output_android/` 各压一个 zip，**排除 `icons/` 和 `images/`**
  （122 MB 逐字节不变的二进制，纯噪音）。HTML 压缩比约 15:1，两个 zip 共 56 MB 而不是 690 MB
- `manifest.json` 记 `pediaCommit`——两个快照的差异可能来自 mod 变了，也可能来自**生成器变了**，
  diff 自己分不出来，得靠这个字段

#### 脚本与 skill 的边界

**能算出确定答案的部分写脚本，不写进 skill：**

```
scripts/  挑两个归档快照 → 页面清单 diff（新增/删除）
          → 变化页面的正文 diff（HTML 需先剥标签规范化）
          → 按章节/实体归类、合并同一实体的多字段变化
          → 输出结构化摘要（不是 raw diff——上次 mod 更新 json/ 变了 635 个文件，
            原始 diff 会淹掉 agent）
skill/    读摘要 + 公告 → 起草条目 → 校验 [] 实体链接能否解析到页面
```

好处：脚本输出每次一致，不会因 agent 而异；且**脱离 agent 也能跑**。

#### 放哪里

**放百科仓库的 `.claude/skills/` 和 `scripts/`，不是用户级 `~/.claude/`。**
连同 prompt 和前置条件一起提交。这个方案把负担全压在维护者一个人身上——而「一个人扛」
正是旧系统的死法。要让它活过维护者，工具必须在仓库里，不能留在本地环境和脑子里。

#### 覆盖率指标

旧系统真正致命的是**死得无声无息**，一年多没人写也没有任何东西报错。这和本项目其它所有
缺陷是同一失效类型（见 [known-issues.md](known-issues.md)）。所以新系统从第一天就要带一个
覆盖率数字接进 `Main audit`：**影响玩法的变更里有多少条有 changelog 条目**。掉下去立刻看得见。

#### 落地顺序

1. ~~先做归档自动化（含 `json/`）~~ **已完成，见上。** 注意新旧快照形状不同：
   `snapshots/<日期>/` 有 `json/`，顶层那 20 个只有 HTML。
2. 写脚本，拿 `HDCivilopedia_20260702` 和 `HDCivilopedia_20260807` 试
   （间隔一个多月，页数 10412 → 9606，其中约 800 页是我们清掉的孤儿页）。
   **看到真实变更集之后再定 schema**，比现在凭空设计准得多。
3. 开始把公告随到随存：`Changelog/announcements/<日期>.md`（mod 仓库），
   **别事后翻群**——回溯翻两个日期之间的群记录是典型会衰减的杂活，而且群记录会滚掉。
4. 有了产出再谈机制。到那时不是要求别人干活，而是「已经有了，你确认一下更准」。
5. 新路径能产出百科更新页之后，再删旧的 691 行解析器
   （`changelog/Changelog.java` + `ChangelogResource.java`）。
   **`.txt` 别删**——那是 1.2~1.4 段历史的唯一记录，是数据不是代码。

### 2. 搜索：拼音和排序已完成，还剩三条

还剩：

- **只搜标题**。描述、`LOC_` 标签、分类名都不参与匹配——搜「航空」找不到机场，

  手机端尤其值得算笔账。扩到标签/描述会让这个数字继续涨，**两件事得一起权衡**。

还有约 507 个标签没有图标，素材只存在于 `.blp` 包里。三条路都堵住了：

   在游戏内百科页面里逐条截图，理想情况用 **Lua 控制百科翻页**。这是社区实际在用的路子
   （Sukritact's Texture Extractor 同源），但工作量大，暂不启动。

素材若哪天到位：丢进 `mods.folder` 或 Steam 库任意位置（现在会自动扫到）→ 重跑 `after_init`
→ 看 `searchEntriesNoIcon` 有没有降。

### 性能

**当前不是瓶颈，建议排在功能之后**：日常迭代只需要 `page`（130s），整轮 190s 也不算难受。
而且这些改动动的正是 `Model.load()`，和功能开发撞车；`Main audit` 现在能自动验收「产物不变」，
真要做的时候有工具了。

- **批量查询消除 N+1**（中风险、收益大）：`Building.load()` 对每个建筑发 14 条子查询，
  Unit/Technology/Civilization 同类。改为每张子表一次性 `select *`，内存里按外键分组装配。
  以 Building 为样板验证产物一致后再推广。
- **多线程**：`linkData` 之前的各 `Model.load()` 相互独立，`write()`、`initIcons()` 同理。
  注意 SQLite `Connection` 非线程安全 → 每线程独立连接，`Db` 改 ThreadLocal。
- **`PreparedStatement`** 替换字符串拼接（性能 + 防注入）。
- **写 JSON 聚合**：`Writable.writeJSON()` 每个对象都重读+重写 `contents.json`，可改内存聚合最后落盘。
- **HTML 渲染**：`Page` 用 DOM+Transformer 序列化上千文件，可评估改 `StringBuilder` 或模板。

### 其它工程化

- 升级 `maven-shade-plugin`（1.2.1 → 3.x），让 `mvn package` 在现代 JDK 可打 fat jar。
- **增量构建**：按内容 hash 跳过未变对象。
- `manual/output` 的科技/市政大图目前是外部预渲染手工放入，可评估在代码内生成。

## 元：整理经验并开源

这个项目本身是一份 **Agent 时代软件工程的实践样本**，值得把经验显式整理出来，并把仓库开源。

有些事情在前 Agent 时代做不了，或者代价高到不会去做，而这里已经做了：

- **逆向一个无公开文档的二进制格式**，把「已排除的假设」当作正式产出记录下来
  （[blp-format.md](blp-format.md)）——失败路径的价值第一次被认真保存
- **从产物反查缺陷**而不是从日志：1570 个孤儿页、256 个断掉的图标、31 条失效路径，
  都不是任何报错发现的（[known-issues.md](known-issues.md)）
- **changelog 从「要求所有人写」变成「从产物推导 + 一句话确认」**（见上方第 1 条），
  这是一个组织问题被工具改变了形状，而不是被纪律解决

更值得写下来的是架构层面的转变：**软件不必只是机械化的程序，Agent 可以作为一个环节
被纳入固定流程**。但纳入的方式有讲究，本项目摸索出的边界是：

> **能算出确定答案的部分交给脚本，需要判断的部分交给 Agent，
> 二者之间用结构化数据交接，并且都要有可度量的验收。**

`Main audit` 是这个原则的第一个实例——它让「产物有没有变坏」变成一个可自动比对的数字，
既是给人看的，也是给 Agent 看的；重构完跑一遍就知道有没有搞砸。计划中的 changelog 系统
是第二个实例：脚本产出结构化变更集，Agent 负责措辞与对齐，覆盖率数字兜底。

开源前要处理的：`config.properties` 已经隔离了机器路径（模板在 `config.example.properties`），
但仓库里还有 `.vscode/settings.json`、`manual/wiki/` 的抓取缓存等需要过一遍；
另外 `docs/` 目前是中文，面向外部读者可能需要一份英文说明。

## 已完成

- **性能**：连接复用 + 缓存、`init` 事务化 + PRAGMA + 日志改造。整轮从 ~3 小时降到分钟级，
  详见 [performance.md](performance.md)。
- **历史背景**：走 Wikipedia 缓存（`Main wiki` → `manual/wiki/`），详见 memory 里的说明。
- **搜索（基础版）**：构建期产 `output/{lang}/search-data.js`，前端 `search.js` 做标题子串匹配。
- **搜索：拼音 + 排序**。中文标题里只有 20/2400 条含拉丁字母，打 `jichang` 原本搜不到「机场」。
  - `tools/Pinyin.java` 在构建期把标题转成空格分隔的音节存进索引的 `p` 字段
    （`机场` → `ji chang`）。**音节边界是关键**：前端拼起来做全拼匹配、取首字母做 `jc`
    匹配、按边界起点匹配让 `jichang` 也能找到「国际机场」，同时 `ang` 不会命中音节中段。
  - 两张表由 `scripts/gen_pinyin_tables.py`（pypinyin）生成：
    `manual/pinyin-chars.tsv` 覆盖 U+4E00~U+9FFF **全部** 20924 个字（不只当前用到的，
    这样 mod 加新字不需要人工介入）；`manual/pinyin-words.tsv` 是 38 个多音字词——
    逐字转会把「银行」读成 yinxing、「音乐」读成 yinle、「长矛」读成 zhangmao。
    脚本自己校验 Java 那套「先最长词、再逐字」的算法能复现 pypinyin 的分词结果。
  - 前端改成分档打分：标题精确 → 标题前缀 → 标题子串 → 全拼前缀 → 首字母 → 后续音节起点，
    同档内短标题优先。原来是取索引顺序前 30 条，精确命中会输给靠前的子串命中。
  - audit 加了 `searchEntriesNoPinyin` 和 `searchPinyinUnmapped`（都是 0）：
    没有读音的字会原样留在 `p` 里，于是「表该重新生成了」是个看得见的数字。
- **产物归档自动化**：`tools/Archive.java`，每轮 `page` / `after_init` 后按日归档
  `json/` + 压缩的 HTML + `manifest.json`，详见上面 changelog 一节的「前置」。
- **配置外部化**：四个机器相关路径进 `config.properties`（模板 `config.example.properties`），
  83 条硬编码贴图目录换成扫描根目录自动发现——不会再因 mod 改名而失效。产物逐项不变，
  且 `load()` 从 122s 降到 74s（每次图标查找少 stat 几十个目录）。
- **产物 audit**：`view/Audit.java`，`page`/`after_init` 后自动跑，对比 `manual/audit-baseline.json`
  并标出变差的指标。
- **手机版侧栏**：抽成 `output_android/{lang}/sidebar.js`（原本内联进每一页），加了首页入口和
  点外部/返回键关闭。顺带清掉 1570 个孤儿页面，手机版 198 MB → 163 MB。
- **图标解析修复**：mod 目录改名导致的失效路径、`Tools.getImage` 只赌一行的 bug。
  搜索结果无图标比例 41% → 26%。
